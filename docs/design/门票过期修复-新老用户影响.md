# 门票过期修复：新老用户影响

## 一、新用户（升级后首次购票 / 从未有过门票）

| 项目 | 影响 |
|------|------|
| **购票** | 无变化，仍为 100/300/500/1000 MC。 |
| **首次 72h** | 购票后 72 小时内须完成首次质押，否则门票失效；逻辑与修复前一致。 |
| **赎回后** | 赎回后 72 小时内须再次质押，否则门票失效；**新增保护**，不会因「购票很早」在赎回后被立刻判过期。 |
| **存储** | `lastStakeDeadlineBase` 初始为 0，首次过期判断仍用 `purchaseTime`；赎回后由合约写入赎回时间。 |

**结论**：新用户只多一层「赎回后 72h」保护，行为更符合预期，无不利影响。

---

## 二、老用户（升级前已购票、已质押或已赎回）

### 2.1 当前仍有有效质押（未赎回完）

| 项目 | 影响 |
|------|------|
| **当前状态** | 有未到期质押，门票有效，可领收益、到期可赎回。 |
| **升级后** | `lastStakeDeadlineBase` 为 0（未写入过）。 |
| **到期赎回后** | 赎回瞬间写入 `lastStakeDeadlineBase = block.timestamp`，之后按「赎回时间 + 72h」判过期。 |
| **对比修复前** | 修复前赎回后可能立刻被判过期；修复后赎回后有 72h 可再次质押。 |

**结论**：老用户中有未赎回质押的，**只受益**：赎回后不再被立刻判过期。

---

### 2.2 已赎回且无质押（门票仍有效，未触发过期）

| 项目 | 影响 |
|------|------|
| **当前状态** | 曾质押并赎回，当前无有效质押，但门票未被过期逻辑清掉（例如还未再次调用到 `_expireTicketIfNeeded`）。 |
| **升级后** | `lastStakeDeadlineBase` 仍为 0。 |
| **下次操作** | 一旦某次调用触发 `_expireTicketIfNeeded`，修复前会按「购票时间 + 72h」判过期（可能立刻失效）；修复后仍用 `purchaseTime`（因 lastStakeDeadlineBase=0），行为与修复前一致。 |
| **若在 72h 内再次质押** | 修复前后都是：有质押就不判过期，门票保持有效。 |

**结论**：这类老用户升级后行为与修复前一致；若之前「购票已超 72h」且一直没再质押，仍可能在下次触发时被判过期（与修复前相同）。

---

### 2.3 已因过期被销毁门票的老用户

| 项目 | 影响 |
|------|------|
| **当前状态** | 合约里门票已清（amount=0 等），无法再质押、无法再赎回。 |
| **升级** | 合约逻辑无法自动恢复已清掉的门票。 |
| **恢复方式** | 只能通过**运营/管理员**：用 `export-ticket-expired-users.cjs` 导出名单，再对每个用户执行 **adminSetUserTicket 恢复门票** 或 **链下退 MC 补偿**。 |

**结论**：已过期用户不会因本次升级自动恢复，需按「门票过期修复方案」做人工恢复或补偿。

---

## 三、汇总表

| 用户类型 | 升级后行为变化 | 是否需要额外操作 |
|----------|----------------|------------------|
| **新用户** | 赎回后多 72h 窗口，更合理 | 否 |
| **老用户 - 仍有有效质押** | 赎回后不再被立刻判过期 | 否 |
| **老用户 - 已赎回、门票仍有效** | 与修复前一致（仍按购票+72h） | 否 |
| **老用户 - 门票已被过期销毁** | 合约不自动恢复 | 是：需管理员恢复门票或链下补偿 |

---

## 四、数据与存储

- **升级不丢数据**：新变量 `lastStakeDeadlineBase` 通过 __gap 预留槽位加入，原有 user、ticket、stake 等数据不变。
- **老用户默认值**：未发生过「赎回后无质押」的，`lastStakeDeadlineBase` 保持 0，过期逻辑仍用 `purchaseTime`，与修复前一致。
